# Super Scholar V3.9.1 — Candidate Source Resolution + Provider Profiles

## Scope

This release stays within the current CS MVP: upload/understand research → recommend → compare → select. It does not add fake metrics, acceptance probabilities, or unauthorized JCR/WoS values.

## 1. OpenAlex candidate Venue enrichment

The old V3.9 diagnostic could report `OpenAlex Works Ready` and `Source hydration Ready` while a catalog candidate still showed `Source topic fit = —`. That was possible because only Sources already attached to the semantic-search papers were hydrated.

V3.9.1 adds a second, explicit stage:

```text
semantic Works
  + catalog candidates
       ↓
research-relevant bounded shortlist
       ↓
journal: exact ISSN lookup first
conference/journal fallback: OpenAlex Source search
       ↓
source-type + conservative identity score
       ↓
confident match only → openalexSourceId/topics
       ↓
Research Match
```

No fuzzy result below the identity threshold is attached. Missing resolution stays Unknown. Authenticated OpenAlex uses a wider bounded candidate slice; anonymous mode is intentionally smaller to protect the public API budget.

Recommendation health distinguishes:

- OpenAlex Works
- OpenAlex semantic-paper Sources
- OpenAlex candidate Venue Sources

and records attempted/resolved/resolved-with-topics counts.

The OpenAlex settings diagnostic also exercises candidate Source resolution using a hydrated real Source identity.

## 2. Semantic Scholar key UX and rate limits

The UI links directly to the official key-request form:

`https://www.semanticscholar.org/product/api#api-key-form`

Anonymous/public-pool HTTP 429 is classified as `rate_limited` / `Limited`; an authenticated 429 is separately described. API keys are sent only in the official `x-api-key` request header and are encrypted in local persistence.

## 3. Independent AI provider profiles

`ai_provider_profiles` stores OpenAI, DeepSeek and Custom independently. Switching the active provider only changes the selected profile; it does not rewrite the other providers' Base URL/model/protocol/output/capability flags/API key. The current page session also preserves unsaved drafts while switching cards.

Migration `20260829_0008` copies the currently active legacy provider into the new table for backwards-compatible upgrades.
