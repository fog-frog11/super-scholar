# Super Scholar V3.6.1 — Provider JSON Compatibility Hardening

This patch fixes a failure mode where a custom OpenAI-compatible provider successfully completed and billed a text extraction request, but Super Scholar aborted the whole research-understanding run because one returned field did not satisfy the local Pydantic contract.

## Reliability changes

- Provider/network failures remain fail-fast with SDK retries disabled.
- Local JSON-contract imperfections no longer throw away a successful paid text call.
- Valid chunk fields are validated item-by-item; invalid CCF areas/facts are dropped while valid grounded facts are kept.
- If the outer JSON is malformed/truncated, the chunk falls back to a conservative local evidence summary and the pipeline continues without sending a repair request.
- Edge-safe text extraction output budget is raised from 700 to 1,100 tokens while the prompt is capped at 12 concise research-level facts.
- Final synthesis remains protected by the existing deterministic fallback.

## Diagnostics

- The original phase name (for example `text research chunk 4/6`) is preserved.
- Diagnostics now expose the local validation message, raw output character count, response head, and response tail.
- The frontend renders warning vs error states separately and shows the validation message.

## Connection probe

- `researchProbe` now validates the same CCF-code, fact-category, confidence, and evidence-ID constraints that matter in the real extraction pipeline.
- A gateway can no longer pass ResearchProbe merely by returning any JSON object with a `summary` field.

## Structured Outputs

- Selecting JSON Schema now requests `strict: true` for Responses-compatible providers.
- Chat Completions now honors the configured JSON Schema mode instead of always degrading to JSON Object mode.
- JSON Object remains the compatibility mode for gateways that do not implement Structured Outputs.

## Verification

- Backend compile/test suite: **37 passed**.
- Frontend typecheck/build was not executed in the packaging environment because `frontend/node_modules` was not present; the TypeScript change is limited to diagnostics rendering and uses existing `Badge` tone values.
