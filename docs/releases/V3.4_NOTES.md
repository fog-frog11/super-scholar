# Super Scholar V3.4

## Why this release exists

V3.3 correctly stopped duplicate/retried provider calls, but a custom gateway behind Tencent EdgeOne could still return HTTP 554 after ~18 seconds even for one bounded chunk. Tencent EdgeOne documents 524/554 as an origin-response timeout after the edge has connected to the origin and forwarded the request. This explains the observed combination of provider-side token billing plus no usable client response.

V3.4 changes the research transport, not the research semantics.

## Streaming transport

- Responses API research calls use SSE (`stream=true`) when streaming is enabled.
- Chat Completions research calls use streaming chunks when streaming is enabled.
- The client still uses `max_retries=0`; one planned provider call is one HTTP request.
- Responses streams must reach `response.completed`; an EOF before a terminal event is treated as an error and partial JSON is discarded.
- Chat streams must reach a non-null `finish_reason`; incomplete streams are rejected.
- Structured JSON is accumulated locally from streamed text deltas and validated exactly as before.

## Settings

The Model & Parsing page now contains **Streaming transport (recommended)**.

It is enabled by default for OpenAI, DeepSeek and custom providers. The provider diagnostic adds a real streaming test and reports time to first SSE event (TTFE). This is especially useful for CDN/reverse-proxy endpoints.

## Tencent EdgeOne 554 diagnostics

If a response is HTTP 554 and the response header identifies `TencentEdgeOne`, Super Scholar now explains the precise failure category:

- non-streaming request: enable SSE streaming;
- streaming request: EdgeOne still received no usable origin response before its timeout, so the remaining fix belongs to the gateway/operator (origin response timeout, SSE flushing, or a direct endpoint bypassing EdgeOne).

Super Scholar cannot repair a CDN origin timeout after the request has left the application.

## Existing safeguards remain

- hierarchical evidence chunks;
- fail-fast on the first provider/API failure;
- SDK retries disabled;
- bounded provider-call budget;
- no raw-PDF upload in the research pipeline;
- evidence grounding and strict local validation;
- vision-only PDF support;
- OCR fallback;
- encrypted local API-key storage.
